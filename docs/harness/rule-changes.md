# 규칙 추가·수정·삭제 절차 (사용자 승인 필수)

> 범위: **공통** (`PTK_V2_FE` · `PTK_V2_BE` 동일). 출처 태그 정의는 `README.md` 참고.

## 1. 원칙

- **[U 2026-11-27]** 대화하면서 사용자가 하는 말(새 규칙·선호·반복되는 지적)은 앞으로도 계속 생긴다. 하네스에 **항상 추가하되, 추가하기 전에 사용자에게 먼저 물어본다.**
- 에이전트·작업자는 **승인받지 않은 규칙을 하네스 파일에 쓰지 않는다.** 사용자가 거절한 규칙은 기록하지 않는다.
- 수정·삭제도 추가와 똑같이 사용자 승인이 필요하다.

## 2. 규칙 후보를 알아채는 신호 [D]

다음 중 하나가 보이면 "규칙 후보"로 취급하고 §3 의 질문을 한다.

- "앞으로는 …", "항상 …", "절대 …하지 마", "…로 통일하자" 같은 표현
- 같은 종류의 지적을 사용자가 두 번 이상 한 경우
- 사용자가 결과물을 바로잡으며 **기준**(색 · 라운드 · 용어 · 절차)을 알려준 경우

한 번 쓰고 끝나는 일회성 지시(예: "이 화면만 이렇게 해줘")는 규칙 후보가 아니다. 애매하면 규칙 후보로 보고 묻는다.

## 3. 사용자에게 묻는 방법 [D]

해당 작업 응답의 **끝에서** 아래 4가지를 한 번에 묻는다 (선택지는 추천안을 맨 앞에 둔다).

1. **원문 인용** — 사용자가 한 말 그대로
2. **적용 범위** — FE / BE / 공통
3. **제안 문구** — 하네스에 들어갈 문장 (태그 `[U]` 로 기록될 예정)
4. **충돌 여부** — 기존 규칙과 겹치거나 모순되는 곳이 있는지

## 4. 승인된 규칙을 반영하는 방법 [D]

1. 규칙 변경도 하나의 작업이므로 `workflow.md` 절차(이슈 → 브랜치 `docs/<이슈번호>` → 커밋 → PR → 머지 → 브랜치 정리)를 그대로 따른다.
2. 범위가 **공통**이면 FE · BE **두 레포 모두** 같은 내용으로 반영한다 (각각 이슈·PR).
3. 규칙은 알맞은 문서에 **출처 태그와 날짜**를 붙여 추가한다: `**[U 2026-12-03]** 문장`.
   - 공통 규칙 → `ai-operating-protocol.md` 또는 `workflow.md`
   - 레포별 규칙 → `project-rules.md`
   - 구조 규칙 → `architecture.md`, 검증 규칙 → `verification.md`
4. `docs/harness/changelog.md` 표에 한 줄을 추가한다: 날짜 · 변경 내용 · 태그 · 근거(사용자 발언 요약) · 관련 이슈/PR.
5. 규칙이 코드·문서와 어긋나게 되면 같은 PR 에서 함께 고치거나, 불일치 이슈를 따로 만든다.

## 5. 태그 승격 [D]

- `[D]`(기본값) 항목을 사용자가 검토해 **그대로 두기로** 하면 `[A 날짜]` 로, **고치라고** 하면 수정한 뒤 `[U 날짜]` 로 바꾼다. 이때도 `changelog.md` 에 기록한다.
